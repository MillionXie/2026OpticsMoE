## 为什么待提交列表会这么大

原 119,129 个未跟踪文件中有 92,595 个 PNG，另有 15,588 个 `node_modules` 文件。
最重的目录是几份 T12 交付/导出包和旧展示材料，并非新写了十万份模型代码。
忽略规则只排除安装依赖、私有临时区、handoff 中的二进制交付产物。

规则不隐藏 handoff 内 Python/YAML/Markdown/JSON/CSV，不会让已经被 Git 跟踪的
证据消失，也没有删除任何文件。剩下仍有两千多份 Python 文件，包括交付包里的
源码快照和本地独有实现，不能继续一把忽略来追求数字好看。
旧测速/功耗资料仍保留，正式报告与源代码须继续按任务审计纳入主线。

## 为什么还可能看到“10k+”版本差异

本批之前实际复查：当前工作目录的提交与 `main` 直接比较为
1538个路径、249164行增加、9995行删除；使用共同祖先比较则是另一组更大的数字。
这是 **两份提交之间的差异**，不代表这次删除了9995行工作文件，
也不代表有9995个未提交修改，更不是9995条分支。

当前工作目录仍在旧 T12 分支，其历史与逐任务发布的 main 不是同一条提交链。
主线已经吸收部分正确源码，但未完成迁移的任务仍须保留旧运行入口；
不能整仓 merge、reset 或直接 checkout main，让 UI 数字归零。
只读工具：[inspect_git_noise.py](inspect_git_noise.py)，能分别输出这些数量。

## 29条旧分支如何保护

逐项 HEAD/用途/恢复映射：[LOCAL_INACTIVE_BRANCH_RECEIPT_20261004.json](LOCAL_INACTIVE_BRANCH_RECEIPT_20261004.json)。
不是“已经全部合入main”：未合入的历史源码也保留，不擅自决定废弃算法版本。

- 每条完整提交保留于 `refs/archive/local-inactive-20261004/<原分支名>`。
- 私有 Git 包：`.codex_tmp/git_branch_archive_20261004/inactive_local_branches.bundle`。
- SHA256：`b088e2b10552f19651a63c41e1d6770ab032bb881d1e50d8c3a42fbae29af47d`。
- 包已通过 `git bundle verify` 与29条HEAD映射检查；它以已保留的main
  `22623fb5a2aa2353a8e8ff4afdf88626f265e797` 为前提，不是一个独立完整克隆。
- 原Git配置私有备份也保留；本批未删旧分支配置段，不能称配置文件已完全归一。
- 删除名称使用旧SHA条件核验和Git引用事务；未使用强推、强制分支删除、硬重置或GC。
- HEAD/main/index/已跟踪改动/工作树列表操作前后均一致；不修改远端引用。

需要恢复名称时，经用户要求再执行：

```sh
git branch <原分支名> refs/archive/local-inactive-20261004/<原分支名>
```

恢复提交不等于恢复未提交源码；现有含修改的工作树没有纳入本批取消名单。
测速/功耗分支取消的只是日常开发名称，它们的源码历史和原测量文件没有被删除。
